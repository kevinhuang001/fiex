# 软件需求与测试追溯

本页把当前 Core 主分支中可观察的用户行为、插件合同和质量要求拆成稳定编号，并指向能验证它们的测试。代码基线见[文档代码基线](/reference/source-baseline)。若某项需求来自尚未合入的变更，会明确标成待合入；它不代表当前主分支已经实现。需求也不代表所有平台、文件系统或插件服务都已经被测试。

路径约定：E2E 路径相对仓库根目录；表中只写 `browsing.spec.ts` 等短名时，默认位于 `e2e/explorer/`。前端单元测试短路径相对 `src/`；Core Rust 短路径相对 `src-tauri/src/`，独立 crate 的测试路径会注明 crate 名。加粗的测试名称对应测试标题或 Rust 测试函数；CI job、人工平台检查和待合入用例会另行标明。

## 如何读这份追溯表

| 标记 | 验证类型                     | 可以证明                                           | 不能单独证明                                 |
| ---- | ---------------------------- | -------------------------------------------------- | -------------------------------------------- |
| UT   | TypeScript / Rust 单元测试   | 纯逻辑、转换和策略在给定输入下正确                 | 完整窗口、操作系统和真实文件系统行为         |
| UI   | React 组件测试               | 受控组件的呈现、状态或点击反馈                     | Tauri 命令、原生对话框和系统权限             |
| E2E  | Playwright 浏览器测试        | 用户流程在浏览器 harness 和隔离 fixture 中连贯工作 | 真实系统 Trash、文件选择器、沙箱或账号服务   |
| INT  | Core 与外部插件进程集成      | IPC 握手、请求、返回、并发和进程关闭路径           | 所有第三方服务及其生产故障                   |
| FM   | Kani、覆盖率和 mutation 检查 | scope-policy 已建模的性质及测试对逻辑变化的敏感性  | 未建模的 UI、OS、网络或 provider 逻辑        |
| PLAT | 平台构建或原生集成检查       | 对应 runner / OS 路径确实执行                      | 未列入工作流的 OS 版本、驱动、账号和用户配置 |

测试路径表示仓库中有对应验证；每次变更是否通过，以该 PR 的 Actions 结果为准。没有自动化证据的行会明确列出人工或平台验证缺口。

## 已知自动化覆盖缺口

- 浏览器 E2E 使用确定性 fixture；它不访问真实 Finder/Explorer Trash、OS 应用选择器、磁盘权限对话框或设备挂载。
- 原生拖放录像覆盖特定 OS runner 和用例，和每次 Core PR 的 Browser UI job 不同；检查 `.github/workflows/recording.yml` 的实际运行状态与 artifact。
- macOS 有 Trash Put Back 专项回归；Windows/Linux 的真实系统 Trash、权限设置、不同桌面环境和 OS 版本仍需平台检查。
- Google OAuth、WebDAV、SMB、Git 服务端登录与网络故障恢复不能由 Core fixture 证明；需运行官方插件仓库对应 CI，真实账号流程还需独立测试账号。
- 屏幕阅读器、键盘全程可达、磁盘耗尽、系统休眠中断及进程崩溃后的远程上传恢复尚无完整验收矩阵。

## 需求变更时的更新规则

1. 为新行为分配稳定 ID，并写成用户可观察的验收条件。
2. 给纯逻辑、IPC 边界和完整界面路径分别安排 UT、INT 和 E2E；涉及原生系统 API 时增加 PLAT 验证。
3. 权限或资源范围变化必须更新负面测试；scope-policy 变化要检查 Kani、coverage 和 mutation job。
4. 在变更同一 PR 中更新本页的需求行、正向测试索引和未覆盖项。
5. 只记录仓库中能定位到的测试；若证据只在另一个仓库或平台 artifact 中，明确写出来源和限制。
6. “测试定义存在”不等于“本次执行通过”。报告结果时引用具体 commit 的 Actions 状态。

当前 CI job 与命令以[格式、构建与 CI](/developer/quality-ci)和仓库工作流为准。
